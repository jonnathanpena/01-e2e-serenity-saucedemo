ESTADO DEL TEST PRINCIPAL (@smoke)
-----------------------------------
El codigo cubre el flujo completo: Login → Productos → Carrito →
Checkout → FinishThePurchase → verificacion del mensaje de confirmacion.

El test falla con TimeoutException esperando el boton #finish.
Causa raiz identificada: EnterWithJS.java asigna el valor usando la
propiedad directa del DOM (element.value = value), pero React 16+
intercepta el setter nativo de HTMLInputElement.prototype. Al saltarse
ese setter, el estado interno de React no registra el cambio en el
campo #postal-code y lo trata como vacio. La validacion del formulario
falla silenciosamente al hacer click en #continue y el navegador
permanece en la pantalla del formulario, nunca llegando al overview
donde aparece #finish.

Solucion exacta en EnterWithJS.java (3 lineas):
  Reemplazar la asignacion directa:
    element.value = '';
    element.value = value;
  Por el setter nativo que React si intercepta:
    var nativeInputValueSetter = Object.getOwnPropertyDescriptor(
        window.HTMLInputElement.prototype, 'value').set;
    nativeInputValueSetter.call(element, value);

HALLAZGOS TECNICOS
------------------
1. REACT CONTROLLED INPUT (root cause del fallo):
   SauceDemo es una Single-Page Application construida en React.
   Los inputs controlados por React 16+ tienen su setter nativo
   sobreescrito por el propio React para trackear cambios de estado.
   Selenium/Serenity usa sendKeys que llama al metodo nativo, pero
   en modo headless la cadena de eventos puede interrumpirse.
   La clase EnterWithJS fue implementada como solucion usando
   JavascriptExecutor: asigna el valor y dispara eventos 'input' y
   'change'. Sin embargo, la asignacion directa a element.value no
   pasa por el setter nativo de React, por lo que el estado interno
   de React no detecta el cambio. Ver "Solucion exacta" arriba.

2. PATRON SCREENPLAY:
   El patron Screenplay demostro alta mantenibilidad: cada
   responsabilidad (Task, Question, Target, Interaction) esta en su
   propio archivo. Un cambio de locator impacta UN solo archivo.
   Un cambio en la estrategia de interaccion con React (el fix)
   impacta SOLO EnterWithJS.java, sin tocar ninguna Task.

3. SELENIUM MANAGER:
   La gestion automatica del chromedriver con Selenium 4 elimina
   la necesidad de WebDriverManager externo. Funciono correctamente
   en macOS arm64 y el entorno de GitHub Actions (ubuntu-latest).

4. SERENITY REPORTS:
   El reporte HTML de Serenity genera documentacion viva (Living
   Documentation) con los pasos de Gherkin, capturas de pantalla
   configurables y metricas de ejecucion. Configurado actualmente
   en FOR_FAILURES; el valor optimo para documentacion completa
   es AFTER_EACH_STEP.

5. GITHUB ACTIONS CI (pipeline activo, falla por el bug de React):
   Se configuro un pipeline en .github/workflows/ci.yml que ejecuta
   ./mvnw verify con Java 21 y Chrome headless en ubuntu-latest.
   El pipeline falla en el step de finalizacion de compra por el
   bug de React descrito en el hallazgo 1.

   El diseno del pipeline demuestra el patron esencial de CI para QA:
   uso de "if: always()" en los steps de publicacion de artefactos.

   Por que "if: always()" es critico:
   En GitHub Actions, cuando un test falla, los steps siguientes
   se saltan por defecto. Sin "if: always()", el reporte Serenity
   (target/site/serenity/) y los resultados de Failsafe nunca se
   subian cuando el test estaba rojo. El equipo no tendria evidencia
   disponible y tendria que reproducir el fallo localmente para
   diagnosticar.
   Con "if: always()", el reporte queda disponible como artifact
   descargable incluso cuando el build esta en rojo, permitiendo:
   - Ver el screenshot del navegador en el momento del fallo.
   - Identificar el step exacto que fallo en el reporte Serenity.
   - Compartir la evidencia con el equipo sin acceso al agente CI.
   Este patron es estandar en equipos de QA maduros y es una de las
   primeras configuraciones que debe hacerse al montar un pipeline.
