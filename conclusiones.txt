CORRECCIONES APLICADAS EN ESTA SESION
--------------------------------------
1. EnterWithJS.java [CORREGIDO - ya estaba implementado correctamente]
   La clase ya usaba Object.getOwnPropertyDescriptor para obtener el
   native setter de HTMLInputElement.prototype y disparar los eventos
   'input' y 'change' con bubbles:true. Este era el fix correcto para
   React controlled inputs. No requirio cambios adicionales.

2. Login.java [CORREGIDO]
   Problema: URL de SauceDemo hardcodeada como Open.url("https://...").
   Efecto: Ignoraba webdriver.base.url de serenity.conf.
   Fix aplicado: Open.relativeUrl("/") para que la URL base del
   archivo de configuracion sea la fuente de verdad.

3. serenity.conf [ACTUALIZADO]
   - Agregado: webdriver.base.url = "https://www.saucedemo.com"
   - Cambiado: take.screenshots = AFTER_EACH_STEP (antes FOR_FAILURES)
     Beneficio: el reporte Serenity genera living documentation
     completa con captura en cada paso del escenario.

4. StageSetupHooks.java [CORREGIDO]
   Problema: Ausencia de hook @After para limpiar el Stage de Serenity
   entre escenarios.
   Fix aplicado: Agregado @After con OnStage.drawTheCurtain() para
   cerrar el driver del actor al finalizar cada escenario y garantizar
   sesion limpia en el siguiente.
   Nota: clearBrowserState() con Serenity.getDriver() se mantiene en
   @Before(order=20) para eliminar cookies y localStorage antes de
   cada escenario. Genera una segunda instancia de Chrome (Chrome #1)
   ademas del driver del actor (Chrome #2); esto es un trade-off
   aceptado para asegurar limpieza de estado.

5. AddItemsToCart.java [CORREGIDO - causa del fallo en GitHub Actions CI]
   Problema: Click.on(ADD_TO_CART_BUTTON) no disparaba el event
   handler de React en Chrome headless de ubuntu-latest. El step
   "agrega al carrito" reportaba exito (el elemento fue encontrado y
   clickeado) pero el item no se agregaba al localStorage de React.
   Consecuencia: la pagina del carrito mostraba 0 productos en CI.
   Fix aplicado: ClickWithJS.on(ADD_TO_CART_BUTTON) que usa JavaScript
   element.click() y si propaga el evento sintetico de React.

6. OpenTheCart.java [CORREGIDO]
   Problema: Click.on(CART_LINK) no completaba la navegacion a
   /cart.html en Chrome headless con dos instancias activas. React
   Router intercepta el click del icono del carrito y no lo procesaba
   via Selenium nativo.
   Fix aplicado:
   a) Open.relativeUrl("/cart.html") para navegar directamente sin
      depender del event handler de React Router.
   b) WaitUntil.the(CartPage.CHECKOUT_BUTTON, isVisible()) como guard
      para confirmar que el cart page cargo completamente antes de que
      CartItemCount intente contar los [data-test='inventory-item'].
      El boton #checkout es exclusivo de /cart.html (no existe en
      /inventory.html), por lo que es un selector confiable como
      indicador de carga de pagina.

7. Checkout.java [CORREGIDO]
   Problema: Click.on(CartPage.CHECKOUT_BUTTON) no navegaba a
   /checkout-step-one.html. El boton dispara React Router navigation
   y el evento sintetico no se propagaba con Selenium nativo en
   Chrome headless.
   Efecto: WaitUntil.the(FIRST_NAME_FIELD, isVisible()) expiraba tras
   10 segundos con "no matching element found by [#first-name]".
   Fix aplicado: Open.relativeUrl("/checkout-step-one.html") para
   navegar directamente. WaitUntil para #first-name se mantiene como
   guard de carga de pagina.

HALLAZGOS TECNICOS
------------------
1. REACT SYNTHETIC EVENTS vs SELENIUM NATIVO (root cause de multiples fallos):
   SauceDemo es una SPA en React. Sus botones interactivos (Add to cart,
   Checkout, enlaces del React Router) registran event listeners
   sinteticos que React gestiona sobre el DOM real.
   WebElement.click() de Selenium invoca el evento nativo del navegador.
   En Chrome headless con multiples instancias de WebDriver activas,
   estos eventos nativos no siempre llegan al layer sintetico de React.
   Consecuencia observable: el click "ocurre" (Selenium no lanza
   excepcion, el elemento fue encontrado) pero la accion de negocio
   (agregar al carrito, navegar) no se ejecuta.
   Patron de solucion aplicado en todo el proyecto:
   - Botones React interactivos: ClickWithJS.on() via JavaScript
     element.click() que si propaga el evento sintetico.
   - Navegacion por React Router: Open.relativeUrl("/ruta") para
     navegar directamente sin depender del event handler.
   - Inputs React controlled: EnterWithJS con native value setter y
     disparo de eventos 'input'/'change' con bubbles:true.

2. DOBLE INSTANCIA DE WEBDRIVER (efecto de clearBrowserState):
   clearBrowserState() llama a Serenity.getDriver() que crea Chrome #1
   (driver global de Serenity). OnlineCast.actorNamed("Standard") crea
   Chrome #2 (driver del actor via WebdriverManager.getWebdriverByName).
   El actor usa Chrome #2 para todas sus interacciones. Chrome #1 queda
   abierto durante toda la duracion del escenario.
   Este escenario amplifico el problema de React synthetic events:
   Chrome #1 en about:blank + Chrome #2 en la SPA causaban que las
   llamadas de Selenium priorizaran el contexto del driver global.
   La combinacion de Open.relativeUrl() y ClickWithJS resolvio el
   comportamiento inconsistente entre local y CI.
   drawTheCurtain() en @After cierra Chrome #2 (driver del actor) al
   finalizar cada escenario pero NO cierra Chrome #1 (global). Este
   comportamiento es conocido y aceptado en Serenity BDD; el driver
   global se gestiona por el lifecycle de la JVM.

3. DIFERENCIA LOCAL vs CI (GitHub Actions ubuntu-latest):
   En macOS local (Chrome 149), Click.on() funcionaba para algunos
   elementos React gracias al renderizado GPU con mayor tolerancia
   en el procesamiento de eventos.
   En ubuntu-latest (Chrome 148, headless estricto), los mismos clicks
   fallaban de forma consistente. El comportamiento de CI es el de
   referencia: es mas estricto y detecta problemas reales antes.
   Leccion: siempre validar en CI tras cualquier cambio de interaccion.
   Indicador temprano: si un step "pasa" en Serenity pero la asercion
   posterior sobre el estado del DOM falla, sospechar de eventos
   sinteticos no propagados (no de locators incorrectos).

4. PATRON SCREENPLAY - MANTENIBILIDAD CONFIRMADA:
   El patron Screenplay demostro alta mantenibilidad: cada
   responsabilidad (Task, Question, Target, Interaction) esta en su
   propio archivo. Los 7 cambios de esta sesion impactaron archivos
   de forma aislada:
   - Cambio de estrategia de navegacion: solo OpenTheCart y Checkout.
   - Cambio de estrategia de click: solo AddItemsToCart.
   - Cambio de configuracion de URL base: solo Login y serenity.conf.
   - Ningun cambio de locators fue necesario; todos eran correctos.

5. SELENIUM MANAGER (gestion automatica de drivers):
   La gestion automatica de chromedriver con Selenium 4 funciona
   correctamente en macOS arm64 y GitHub Actions ubuntu-latest.
   No requiere WebDriverManager externo ni configuracion adicional.

6. SERENITY REPORTS Y LIVING DOCUMENTATION:
   Con take.screenshots = AFTER_EACH_STEP el reporte HTML de Serenity
   genera evidencia visual completa del flujo. Cada paso del escenario
   Gherkin tiene su captura asociada.
   El reporte es accesible en: target/site/serenity/index.html
   En CI se publica como artifact de GitHub Actions (retencion 7 dias),
   disponible incluso cuando el build esta en rojo (if: always()).

7. GITHUB ACTIONS CI (pipeline estable):
   Pipeline en .github/workflows/ci.yml ejecuta ./mvnw clean verify
   con Java 21 Temurin y Chrome headless en ubuntu-latest.
   Se activa en push y pull_request a la rama main.
   Estado actual: PASSING con los fixes de esta sesion.

   Por que "if: always()" es critico en los steps de artefactos:
   Cuando un test falla, GitHub Actions salta los steps posteriores
   por defecto. Sin "if: always()", el reporte Serenity y los
   resultados de Failsafe no se publicarian cuando el build esta rojo,
   privando al equipo de la evidencia necesaria para diagnosticar.
   Con "if: always()" el reporte queda disponible como artifact
   descargable con el screenshot del fallo, el step exacto que fallo
   y la traza completa de Serenity, sin necesidad de reproducir
   localmente. Este patron es estandar en equipos de QA maduros.
