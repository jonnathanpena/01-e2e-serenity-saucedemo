## Context

The project currently has no CI pipeline. Tests are run manually via `./mvnw verify` on developer machines. The goal is to add a single GitHub Actions workflow file (`.github/workflows/ci.yml`) that replicates this local execution in a GitHub-hosted environment automatically on every push and pull request.

Key constraints from the existing stack:
- Build tool: Maven Wrapper (`./mvnw`), no global Maven installation needed.
- Tests run in the `verify` phase via `maven-failsafe-plugin` (surefire has `skipTests=true`).
- The Serenity report is generated by `serenity-maven-plugin` in the `post-integration-test` phase, output to `target/site/serenity/`.
- `serenity.conf` already configures `--headless=new`, `--no-sandbox`, `--disable-dev-shm-usage`, and `--disable-gpu`, making the suite CI-ready with no extra flags.
- Selenium Manager (`webdriver.autodownload = true`) auto-downloads a compatible ChromeDriver at runtime, so no manual driver setup step is needed.

## Goals / Non-Goals

**Goals:**
- Trigger E2E tests automatically on `push` and `pull_request` events targeting the `main` branch.
- Run `./mvnw verify` using Java 21 on an `ubuntu-latest` runner.
- Upload the Serenity HTML report as a downloadable workflow artifact after every run (including failures).
- Cache the local Maven repository to minimize repeated dependency downloads.

**Non-Goals:**
- Publishing the Serenity report to GitHub Pages or any external hosting.
- Parallel test execution or matrix builds across multiple browsers/OS.
- Modifying `pom.xml`, `serenity.conf`, or any existing source code.
- Supporting environments other than the default (`https://www.saucedemo.com`).

## Decisions

### D1 — Runner: `ubuntu-latest`

`ubuntu-latest` GitHub-hosted runners ship with Google Chrome pre-installed, which is required by Selenium. Self-hosted runners were ruled out because they introduce maintenance overhead and are unnecessary for a single-project challenge.

*Alternatives considered:* `windows-latest` — more complex Chrome/path handling and slower. Self-hosted — operational overhead not justified here.

### D2 — Java setup: `actions/setup-java` with built-in Maven cache

`actions/setup-java@v4` supports `cache: 'maven'` out of the box, which reads `pom.xml` and caches `~/.m2/repository`. This avoids a separate `actions/cache` step while still achieving fast dependency restores on subsequent runs.

*Alternatives considered:* Manual `actions/cache` step — more verbose with no added benefit given `setup-java` already handles it.

### D3 — Headless Chrome: reuse existing `serenity.conf` configuration

`serenity.conf` already includes `--headless=new`, `--no-sandbox`, `--disable-dev-shm-usage`, `--disable-gpu`, and `--window-size=1920,1080`. No extra system properties or environment variables need to be passed in the workflow. This keeps CI configuration minimal and consistent with local runs.

*Alternatives considered:* Overriding via `-Dserenity.driver.capabilities` on the Maven command line — would duplicate configuration and risk divergence.

### D4 — ChromeDriver: rely on Selenium Manager

`serenity.conf` sets `webdriver.autodownload = true`. Selenium Manager queries the Chrome version present on the runner and downloads a matching ChromeDriver at test startup. This eliminates the need for a `setup-chrome` or manual driver installation step.

*Alternatives considered:* `browser-actions/setup-chrome` — unnecessary given Selenium Manager already handles it.

### D5 — Report upload: `actions/upload-artifact` with `if: always()`

`target/site/serenity/` is uploaded unconditionally so that the report is available even when tests fail. This is the primary diagnostic artifact for CI runs.

*Alternatives considered:* Upload only on failure — hides pass details which are also useful for trend analysis.

## Risks / Trade-offs

- **Chrome version drift on runner images**: `ubuntu-latest` updates its Chrome version periodically. Selenium Manager mitigates this automatically, but a breaking Chrome release could briefly break the pipeline before Selenium Manager support catches up. → *Mitigation*: Pin runner to `ubuntu-24.04` if instability is observed.
- **Flaky tests on CI**: Network latency or timing differences between CI and local machines may surface intermittent failures not seen locally. → *Mitigation*: Existing `fluent.wait = 8000ms` and `implicit = 5000ms` timeouts in `serenity.conf` provide reasonable resilience. Investigate specific failures before adding retries.
- **`target/` artifact size**: The full Serenity report including screenshots can be large. → *Mitigation*: `actions/upload-artifact` compresses uploads; default 90-day retention is acceptable for a challenge project.
- **Maven Wrapper permissions**: `./mvnw` must be executable. The file is committed with execute permissions, but if the permissions are lost the workflow will fail with a permission error. → *Mitigation*: Add a `chmod +x mvnw` step before the Maven command as a safety guard.

## Migration Plan

1. Create `.github/workflows/ci.yml` as specified in the proposal (no changes to existing files).
2. Push the branch to GitHub; verify the workflow triggers and the `ubuntu-latest` job completes.
3. Confirm the Serenity report artifact appears in the GitHub Actions run summary.
4. Merge to `main` once the pipeline is green.

**Rollback**: Delete or disable `.github/workflows/ci.yml`. No other files are affected.

## Open Questions

- Should the workflow also run on `push` to feature branches, or only on `main` and pull requests targeting `main`? (Current proposal: only `main` branch + PRs to `main`.)
- Is a specific retention period required for the uploaded Serenity report artifact, or is the GitHub default (90 days) acceptable?
